# Decision Engine & LLM Layer

The RevenueTwin Decision Engine provides a robust, predictable, and fully observable decision pipeline for the autonomous agents. It relies on a deterministic base with the LLM acting exclusively as a decision-support module that generates structured outputs. 

## The Core Pipeline

1. **Complexity Assessment**: Determines `LOW`, `MEDIUM`, or `HIGH` complexity based on the `amount_at_risk` and event type.
2. **Candidate Generation**: Retrieves allowed actions from the specialist agent's `AgentDecisionProfile`.
3. **Deterministic Rule Evaluation**: First-pass evaluation of deterministic rules embedded in the agent's profile.
4. **LLM Invocation**: Only invoked if complexity is `HIGH` or if complexity is `MEDIUM` and no definitive deterministic rule applies.
5. **LLM Context Building**: Filters the customer's vast historical data down to *only* what the specific agent profile declares in `required_context`.
6. **Policy Enforcement**: Passes the recommended action through a strict policy check (e.g., maximum retention offers per 24 hours). If violated, downgrades to `NO_ACTION`.
7. **Confidence Scoring**: Adjusts the LLM's raw confidence based on the complexity of the event and whether the LLM's decision agreed with the deterministic fallback rules.
8. **Final Decision**: Saves the decision as an `AgentDecision` and halts the agent run at `AWAITING_APPROVAL`.

## Agent Decision Profiles

Every agent operates using an isolated `AgentDecisionProfile`. This prevents "prompt bleed" where an agent trying to recover a failed $5 subscription accidentally offers a $50 retention discount meant for churn prevention.

The profile strictly defines:
- **Objective**: The goal of the agent.
- **Required Context**: e.g., `["payment_history", "notification_fatigue"]`
- **Candidate Actions**: e.g., `["RETRY", "ALTERNATE_PAYMENT", "NO_ACTION"]`
- **Hard Constraints**: e.g., `"Do not retry if payment method repeatedly failed recently."`
- **Decision Rules**: Deterministic code evaluated before LLM invocation.

## Fallback & Disagreement

- **LLM Failure**: If the LLM times out or returns an invalid schema, the system catches the error and gracefully falls back to the deterministic rule recommendation, or `NO_ACTION` if no rule applies.
- **Disagreement**: If the rule engine recommends `RETRY` but the LLM recommends `ALTERNATE_PAYMENT`, the system favors the LLM but significantly penalizes the `confidence` score, potentially requiring manual merchant approval.

## No Hidden Reasoning

All reasoning generated by the LLM is mapped to the `DecisionOutput` Pydantic schema:
```json
{
  "decision": "ALTERNATE_PAYMENT",
  "confidence": 0.91,
  "reason_codes": ["ALTERNATIVE_METHOD_HIGH_SUCCESS"],
  "evidence": [{"signal": "UPI_SUCCESS_RATE_90D", "value": 0.94}],
  "rejected_actions": [],
  "risk_flags": [],
  "next_step": "REQUEST_APPROVAL"
}
```
No unstructured "chain of thought" or "internal reasoning" strings are persisted to the database.
